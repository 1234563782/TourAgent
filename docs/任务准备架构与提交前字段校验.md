# 任务准备架构与提交前字段校验

## 1. 变更目的

第一阶段把“能不能执行”与“用户说的内容是否被正确理解”分开处理。

系统先完成结构化槽位提取，并把当前事实合并到已有事项。合并后的事项如果缺少执行所需的基础字段，服务器立即返回 `clarify`，要求用户补充信息；只有字段完整的事项才进入语义复核、正式任务创建和任务队列。

这样可以避免让语义复核模型处理本来可以由确定性 Schema 判断的问题，也避免缺字段的事项先进入队列，再在执行层才发现无法执行。

## 2. 改造前后的流程

改造前，槽位模型提取出任务后，流程容易直接进入语义复核。字段缺失有时由语义复核发现，有时由任务执行器或政策规则发现，导致追问职责分散：

```text
用户消息
  -> JEV 路由
  -> 任务提案
  -> 槽位提取
  -> 语义复核
  -> 创建任务
  -> 加入队列
  -> 执行时再发现字段不足
```

第一阶段改为：

```text
用户消息
  -> JEV 路由
  -> 任务提案
  -> 槽位提取
  -> 合并已有事项
  -> 提交前字段完整性校验
       |-- 缺字段：返回 clarify，停止本轮
       |-- 字段完整
             -> 语义复核
             -> 创建正式任务
             -> 加入任务队列
             -> 执行
```

这里的“提交前”指正式任务提交前。字段完整性校验仍位于槽位阶段，因为此时系统已经知道每个任务的意图、目标事项和合并后的事实，但还没有把任务交给执行图。

## 3. 代码位置

主要实现位于 `business_travel/slots.py`：

- `preflight_task_inputs()`：对合并后的任务事项执行确定性字段校验。
- `_validation_fields()`：从 Pydantic 校验错误中提取字段名。
- `_preflight_question()`：把字段名转换为用户可读的中文追问。
- `extract_slots()`：在 `review_payload()` 之前调用预检查。

领域字段定义继续复用已有契约，不在预检查中复制一份必填字段列表：

- 出行使用 `parse_query_request()`。
- 费用核验使用 `ExpenseFacts.model_validate()`。
- 政策解释暂不使用用户事实完整性门禁。

## 4. 出行任务检查什么

`plan_trip` 通过 `parse_query_request()` 按 `query_scope` 选择具体契约。

| 查询范围 | 最低结构字段 |
| --- | --- |
| `hotel` | `query_scope`、`destination`、`check_in`、`check_out` |
| `transport` | `query_scope`、`origin`、`destination`、`departure_date` |
| `combined` | 交通字段和酒店字段都必须完整 |

如果用户明确要求往返交通，契约还要求 `return_date`。如果只查询酒店，交通字段会按已有契约被视为不适用；如果只查询交通，酒店日期也不作为缺失字段。

例如，用户只说“帮我查郑州酒店”，槽位提取可以先保存 `query_scope=hotel` 和 `destination=郑州`，但预检查会发现 `check_in`、`check_out` 缺失，并返回类似：

```json
{
  "status": "clarify",
  "question": "请补充或核实：出行任务的入住日期、退房日期。",
  "missing_fields": ["check_in", "check_out"]
}
```

这时不会调用语义复核，也不会创建出行任务或访问机票、火车票、酒店供应商。

## 5. 费用核验检查什么

`policy_check` 的第一阶段门禁复用 `ExpenseFacts` 的基础结构约束。当前最低字段是：

- `kind`：费用类型，例如 `hotel`、`transport`、`meal` 或 `local_transport`；
- `expense_date`：实际或计划费用日期；
- `destination`：费用发生地。

例如，用户说“核对郑州酒店费用”，可以识别出费用类型和目的地，但没有费用日期。系统会直接返回：

```json
{
  "status": "clarify",
  "question": "请补充或核实：费用核验任务的费用日期。",
  "missing_fields": ["expense_date"]
}
```

这里的门禁只负责保证进入政策核验流程的基础事实可被契约解析。它不等于政策规则已经判断完成。`mainland_business_trip`、`special_approval`、`long_assignment_days`、职级、入住人数等条件仍由后续政策规则根据业务场景继续判断；缺少这些条件时，政策执行层仍可能返回业务层面的 `insufficient_information` 或 `manual_review`。

## 6. 为什么政策解释暂不做同样的门禁

`policy_explain` 的目标是解释制度、标准、条款、适用条件或个人适用标准。它可能只需要政策文本和用户提出的主题，并不一定需要完整的个人出行事实。

例如，“学校住宿报销标准是什么”不应因为没有目的地、职级或费用日期而被槽位层拒绝。政策解释的完整性由后续政策检索阶段判断：

```text
policy_explain
  -> 构造政策查询范围
  -> 检索政策正文或附表
  -> 检查证据是否足够
  -> 信息不足时由政策流程返回 clarify
```

因此，第一阶段只前置 `plan_trip` 和 `policy_check` 的用户事实完整性，不把政策证据完整性混入槽位预检查。

## 7. 为什么必须在语义复核前检查

语义复核的职责是判断“这些字段是否真的来自用户当前请求、是否有否定、归属、单位、日期或语义冲突”。它适合判断：

- 用户说的是实际费用还是假设费用；
- 日期是否被否定或引用；
- 金额单位是否明确；
- 多个任务是否被错误合并；
- 更新事项是否真的针对指定目标。

它不适合替代 Pydantic 契约做基础字段门禁。缺少日期时，让复核模型猜测或重复说明字段要求，会增加一次模型调用，而且不同模型可能返回不同形式的追问。

现在的顺序是：

1. 槽位模型提取并合并事实。
2. 服务器用确定性契约检查能否进入执行流程。
3. 字段完整后，语义复核检查证据和语义一致性。

所以缺字段请求不会调用 `review_payload()`；字段完整请求仍然会调用它，原有的语义安全门继续保留。

## 8. 更新已有事项时如何判断

槽位模型提交的是增量 patch，例如只提交新的金额或新的出发日期。预检查不会只看这次 patch，而是看 `stage_submission()` 合并后的完整 subject。

例如，已有出行事项已经保存了：

```json
{
  "query_scope": "transport",
  "origin": "长沙",
  "destination": "郑州",
  "departure_date": "2026-11-03"
}
```

用户随后只说“改成 11 月 4 日”。这次 patch 只有新的 `departure_date`，但合并后的 subject 仍包含出发地、目的地和查询范围，因此可以通过预检查。反过来，如果新建事项只有一个目的地，预检查就会要求缺失的日期或交通字段。

## 9. 任务和队列什么时候产生

`extract_slots()` 返回 `status=clarify` 时，`graph.py` 的准备节点会清空本轮的 `task_queue`，把追问放入消息结果，并停止后续执行分支。

只有 `extract_slots()` 返回 `status=ok`，主图才会调用任务协调逻辑，把槽位结果转换成正式任务并生成队列。因而预检查失败不会出现“任务已经排队但执行时才追问”的中间状态。

本阶段没有改变 `tasks.py` 的队列排序、依赖关系或任务生命周期；改动点只是把一类确定性的失败提前到任务提交之前。

## 10. 追问快捷路径（第二阶段）

第二阶段已经把缺字段返回连接到 `AgentState["clarification"]`。它保存的是一个未提交草案，不是正式任务：

```json
{
  "question": "请补充或核实：出行任务的入住日期、退房日期。",
  "missing_fields": ["check_in", "check_out"],
  "items": [{
    "intent": "plan_trip",
    "subject_id": "draft-subject-id",
    "draft_task_id": "draft-task-id",
    "question": "查南京酒店"
  }],
  "draft_slots": {"...": "上一轮合并后的未提交事项"}
}
```

下一轮消息到达时，`graph.py` 把追问摘要交给 JEV。JEV 同时判断这句是否回答待补字段，以及是否另有新的业务目标。回答追问不是意图。只有回答关系明确、四个意图都已判定，且剩余请求不需要更细拆分时，主图才使用服务器生成的路由：回答部分更新 clarification 中列出的 subject，额外目标另建任务。未回答、任一意图不确定，或剩余请求需要更细拆分时，回到普通 `TurnRoute`，避免把新话题并进草案，也避免丢掉未判清的目标。

取消、恢复和重试不是意图，也不进入 `other`。它们由 `TurnRoute` 的任务控制或失败恢复绑定目标。保存当前出差、确认事实和阅读已返回结果仍是 `other`：只有这条任务会进入带 `save_trip` 和 `read_task_result` 的助手节点。因此，只取消不另建 `other`；只保存或只阅读旧结果仍必须有 `other` 任务。

快捷路径随后按以下顺序执行：

```text
用户下一句
  -> JEV 判断是否回答当前追问，并判断是否另有新目标
       |-- 未回答、意图不确定或需要更细拆分：回到普通路由
       |-- 已回答且没有额外目标：只更新 clarification 中列出的 subject
       |-- 已回答且额外目标都明确：更新该 subject，并为额外目标另建任务
  -> 领域槽位增量提取
  -> 合并未提交草案
  -> 再次执行 preflight_task_inputs()
       |-- 仍缺字段：更新 clarification，继续追问
       |-- 字段完整：执行语义复核
  -> 复核通过后，把草案转换成 new_task
  -> reconcile_tasks() 创建正式任务并进入队列
```

这条路径仍保留语义复核，因为“字段齐全”只说明能够执行，并不证明日期、归属、否定和假设被正确理解。补充回答成功前，草案不会写入正式 `slots`，也不会访问供应商或政策执行器。

如果 JEV 不可用、缺少 Key 或返回不确定结果，系统不会猜测用户是否在回答追问，而是保留原 `clarification`，让普通流程处理当前消息。普通流程成功创建新事项后，旧 clarification 会被清除，避免过期草案继续影响后续对话。

## 11. 当前边界

- 预检查依赖现有领域契约；新增执行字段时应先更新契约，再由预检查自动获得新规则。
- `policy_explain` 的证据完整性仍在政策检索阶段处理。
- 语义复核仍可能因为证据、否定、归属或任务关系问题拒绝完整字段。
- 当前只对 `plan_trip` 和 `policy_check` 做字段完整性前置；政策解释仍由检索证据决定是否追问。
- clarification 草案依赖 LangGraph checkpoint 持久化，当前没有额外的独立追问表。
- JEV 只判断“当前消息是否回答追问”，字段值仍由领域槽位模型提取，字段完整性仍由服务器 Schema 校验。
- JEV 判定为否或不确定时，快捷路径不会合并新话题。
- 语义复核门禁放宽尚未纳入本阶段。
