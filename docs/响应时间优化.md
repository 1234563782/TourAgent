# 响应时间优化

本次优化针对旅行规划阶段的供应商查询。交通去程、返程和酒店查询彼此独立时，系统可以同时发起请求，整体等待时间由各查询耗时之和，降低到接近最慢查询耗时。

## 当前实现

通过 `TRAVEL_PLANNER_QUERY_MODE` 控制查询方式：

```dotenv
TRAVEL_PLANNER_QUERY_MODE=parallel
```

- `parallel`：使用有界线程池并发执行本次行程所需的独立查询，默认最多为本次查询阶段数量。
- `serial`：按原来的阶段顺序逐个查询，用于基线和 A/B 实验。

并行只改变查询调度方式，不改变候选筛选、候选选择、政策检查、通勤检查和最终展示。每个查询仍然单独记录状态、错误分类、候选数量和 `duration_ms`；某一个供应商查询失败不会直接丢弃其他查询结果。

途牛适配器的同步 `search()` 会在工作线程中运行自己的异步 MCP 请求，因此当前实现不会在同一个事件循环中嵌套运行 `asyncio.run()`。每个查询还会复制观测上下文，保留 `query_flight`、`query_train` 和 `query_hotel` 的 Langfuse 子观测关系。

## 如何做对比实验

固定同一用户输入、供应商返回、模型、候选模式和重试配置，分别运行：

```dotenv
TRAVEL_PLANNER_QUERY_MODE=serial
```

以及：

```dotenv
TRAVEL_PLANNER_QUERY_MODE=parallel
```

比较首个阶段事件时间、规划阶段总耗时、`query_status[*].duration_ms`、P50/P95 完整响应时间、查询错误率，以及候选结果和政策检查是否一致。

单个 `duration_ms` 只能说明该查询自身耗时，不能代表整个请求耗时。并行模式下，整个规划阶段通常接近最慢查询加调度开销；实际收益需要用相同输入的线上或受控供应商回放测量。

## 后续可优化点

并行查询上线后，再根据观测数据决定是否优化酒店详情补查、通勤查询和模型选择调用。它们只有在输入和业务依赖明确时才适合并行，不能为了缩短时间跳过库存、日期、政策或安全校验。
