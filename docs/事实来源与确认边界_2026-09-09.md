# 事实来源与确认边界

日期：2026-09-09。本阶段实现来源可见和显式确认，不宣称已消除模型语义误判。

## 实现范围

1. 槽位继续使用原有values/evidence，新增程序维护的provenance，不改政策金额。
2. 模型复核仅记为model_reviewed，不自动升级成用户确认或企业系统核验。
3. 新增confirm_facts工具，只接收现有subject_id和revision，不接受模型替换事实。
4. 用户通过CLI确认中断后，记录该事项版本的表述确认；拒绝不记录，陈旧版本不弹确认。
5. 任意字段补丁，包括撤回字段，使整项旧确认失效。空补丁重新查询保留原版本。
6. 政策回答和行程草案显示采用的事实。草案保存包含这些来源和确认状态的快照。
7. 保存草案的确认只授权保存，不自动确认事实，也不代表审批、预订或付款。

## 状态含义

| 状态 | 含义 | 不代表 |
| --- | --- | --- |
| user_statement | 从用户原话提取的字段，有原文证据 | 理解一定正确或现实事实成立 |
| model_inference | 模型归类，例如费用科目 | 用户逐字给出了分类 |
| unknown | 历史状态未记录来源 | 可按当前模型结果补造历史来源 |
| model_reviewed | 模型执行过语义复核 | 用户确认或企业核实 |
| user_confirmed=true | 用户通过确认中断认可当前事项版本的表述 | 企业系统已经批准或验证 |
| business_verified=false | 尚未接入企业事实核验来源 | 可以根据用户确认自动置true |

字段更正后重新确认整个事项，采用保守的版本绑定方式，避免沿用与旧条件相关的确认。
确认元数据存放在现有图状态中；使用PostgreSQL检查点时随状态持久化，不新增独立确认表。
保存的草案将fact_context作为现有JSON内容持久化。本轮没有执行真实数据库迁移或写入。

## 使用路径

先核对费用或查询行程，回答会列出采用的前提。
如表述错误，直接说明更正内容，结构化流程更新后重新核对。
如要确认表述，可明确要求“确认刚才这笔事项的表述”；
主助手调用confirm_facts后，CLI显示该事项的实际值、原文证据及中文确认提示。
只有对显示内容进行肯定确认，才记录该版本的user_confirmed。
这条自然语言路由仍依赖模型，尚未做本轮真实模型验收。

只读查询不会为了取得确认而每次打断用户；未确认前提的核对结果属于条件性结果。
当前项目没有报销提交、预订或支付工具，也没有连接企业审批事实服务。
将来增加这些功能时，必须在真正的执行入口核验身份、权限、业务凭据及操作确认，
不能仅检查user_confirmed。

新增断言覆盖：
- 模型不能通过提交工具伪造来源、用户确认、企业核实元数据。
- 模型复核通过后仍未用户确认，旧记录不会被补造可信来源。
- 确认暂停时不写记录；true才接受，false、字符串和字典不被当成肯定确认。
- 确认仅针对准确事项版本；未知事项、旧版本拒绝。
- 保存草案保留来源但不自动确认事实，确认事实也不会自动保存草案。
- 更正或撤回字段使确认失效，空补丁保留确认。
- 回答展示错误餐次提案对应的计算前提，不把它称作企业已核实事实。
- 自由文本按原值展示，不误用其他字段的枚举翻译。

测试使用脚本模型、合成供应商和临时本地存储，不证明真实模型理解准确率。
前次独立语义验证的餐次误接受仍是已知失败；本轮未修改该失败样例或预期，
也没有以增加确认状态为由把它计为通过。
