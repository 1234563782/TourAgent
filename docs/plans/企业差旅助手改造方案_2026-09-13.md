## 1. 结论与边界

建议保留 LangGraph、FastAPI、PostgreSQL/pgvector 和现有供应商适配器，进行分阶段增量改造。
核心不是增加 Agent 数量或继续堆提示词，而是做到：

1. 按真实查询需求定义契约，不把酒店单查强行当成完整行程。
2. 每个事项有明确状态，缺信息时追问，条件修改后使相关旧结果失效。
3. 每个执行模块只接收必要上下文，用户对话与内部执行消息分离。
4. 用结构化业务结果约束最终回答，保留真实数据和失败状态。
5. 实时推送执行进度及可展示的回答，并支持刷新恢复和重复请求保护。
6. 通过冻结测试集、真实模型评测和链路记录判断改造是否有效。

本方案不承诺任意问题都能答对。可追求的目标是：能力范围内正确处理；信息不足能澄清；
外部服务失败能如实说明；不可核验时不编造结论；超出范围时不假装有能力。

### 1.1 保留与不做

| 项目 | 决策 |
| --- | --- |
| 框架与后端 | 保留 LangGraph 和 FastAPI，不迁回 AgentScope，不新增 Java 服务层 |
| 数据库 | 继续使用 PostgreSQL；政策向量检索沿用 pgvector，不引入 MySQL |
| 查询来源 | 保留途牛、高德等已有适配；密钥从现有配置读取 |
| 多 Agent | 保留主助手与专业模块分工，不按每个工具拆 Agent |
| 业务安全 | 保留身份隔离、事项版本、确定性政策检查、偏好授权和行程保存确认 |
| 政策管理 | 保留文档检索与已审核规则的边界，不让模型自动发布或修改公司政策 |
| 模型 | 首轮不更换；后续只有对照评测证明收益时才调整角色模型配置 |
| 暂不做 | 预订、支付、真实审批、自动长期记忆提取、自进化、多 Agent 自由协商 |

## 3. 目标架构与职责

```text
用户输入 / 明确的界面操作
  -> FastAPI：身份、会话归属、输入校验、请求去重
  -> 主编排图
       -> 当前任务与必要上下文
       -> 理解自然语言 / 校验明确操作
       -> 应用经验证的任务补丁
       -> 检查缺失字段、歧义、依赖和允许的动作
       -> 追问，或派发专业能力
            -> 行程规划专家：交通 / 酒店候选选择与组合
            -> 政策专业工作流：检索、规则核验、来源
            -> 普通助手与工具：闲聊、天气、记忆
       -> 校验业务结果
       -> 受约束的回答与用户确认
  -> 实时事件和最终状态
  -> PostgreSQL：检查点、会话、用户记忆、运行记录
```

### 3.1 主助手不是所有结果的第二个裁判

主助手负责意图、任务拆分、澄清、上下文组织和结果协调，但不重新判断已经确定的政策结论。
LangGraph 控制流、契约校验和权限检查由代码负责，不要求模型自由决定。

规划专家可以在约束内选择真实候选和组合，不是只会被动执行的空壳。
政策专业模块可以直接使用检索和规则代码，不必为了保持“两个子 Agent”而增加一次 LLM 调用。
天气、地图通勤、酒店/交通查询和按用户读取偏好继续作为工具。

只在一个领域需要独立的多步决策、上下文和验收标准时，才考虑新增 Agent。
首轮继续由主图持有任务控制权，不引入自由交接，避免扩大调试范围。

### 3.2 通用性不等于没有业务约束

- 允许：配置化差旅标准、供应商真实接口要求、日期顺序、权限与版本检查。
- 允许：代码枚举任务状态和动作类型。这属于程序协议，不是写死业务答案。
- 不允许：匹配某句测试问题后返回专用答案，或按测试城市、金额补造事实。
- 不允许：为了填满契约，默认用户出发地、批准状态或出差日期。
- 表达理解交给模型；是否允许执行、结果是否符合契约交给代码。

## 4. 第一优先级：拆开查询契约

保留现有 `plan_trip` 作为兼容的规划入口，内部区分用户需要的查询组件。
新增契约应通过现有 Pydantic 模式定义，不复制成互相不一致的多套字段配置。

| 请求类型 | 最小业务信息 | 不应强制要求 |
| --- | --- | --- |
| 酒店查询 | 目的地、入住日期、退房日期 | 出发地、交通方式、出发日期 |
| 单程交通查询 | 出发地、目的地、出发日期、用户指定的交通约束 | 酒店日期、返程日期 |
| 往返交通查询 | 单程信息及返程日期 | 酒店日期 |
| 完整行程 | 用户所选组件的必填信息及跨组件时间约束 | 用户未要求的组件 |
| 通勤估算 | 可定位的起终点，必要时补充城市 | 交通票和酒店订单信息 |

供应商额外必填字段以实际适配器契约为准；例如确实需要人数时再追问或让用户确认默认值。
员工职级等信息是政策核验所需，不应一概阻断公开候选查询；缺失时把政策结果标为待核验。

实施要点：

1. 在 `contracts.py` 定义酒店、交通和组合请求，逐步替代单一完整行程对象。
2. 在 `slots.py` 的任务提交中表达请求组件；由原话与上下文验证，不由缺字段反推意图。
3. 在 `planning.py` 按请求组件构建查询阶段及完整性检查。
4. 修改 `tuniu.py`、`providers.py` 的必要适配边界，不能用假出发地适配酒店接口。
5. 联动修改 `plan_checks.py`、`policy_guard.py` 等实际受影响的校验和展示调用点。
6. 旧检查点保留读取适配；不得把历史完整行程静默推断为酒店单查。

## 5. 任务状态与多轮对话

### 5.1 标识与事实归属

继续区分身份、会话和事项，新增运行标识只用于一次执行：

| 标识 | 用途 |
| --- | --- |
| `company_id`、`user_id` | 来自认证上下文，模型和前端输入不能替换 |
| `conversation_id` | 一段对话，对应现有会话与检查点范围 |
| `task_id` | 一个需要完成的任务，由服务端生成 |
| `subject_id`、`revision` | 复用现有业务事项及版本，绑定事实和结果 |
| `run_id` | 一次执行尝试，用于进度、追踪和恢复 |
| `request_id` | 客户端请求幂等标识；同一身份和会话内校验 |

新增任务层关联现有事项，不把事实同时复制到多处长期维护。
任务记录保存意图、组件、事项引用、状态、待澄清项、依赖和结果引用。
派发时使用绑定版本的快照，禁止子模块读取后来变化的事项并冒充当前任务结果。

### 5.2 建议状态

```text
collecting -> needs_clarification -> ready -> running
                                      running -> completed / partial / failed
                                      running -> awaiting_confirmation
非终态 -> cancelled
```

状态转换由代码决定，模型只能提交建议和有来源的事实补丁。
查询完成和持久化确认是不同事项：只读查询不强制要求用户点确认；
行程保存沿用人工确认，偏好修改沿用现有明确授权或候选确认机制。
等待澄清不是 LangGraph 人工授权中断，不能使普通补充信息被确认锁挡住。

### 5.3 关键对话行为

- 缺信息：问当前任务真正缺少的信息，不把字段校验错误原样扔给用户。
- 存在歧义：针对歧义追问，不能把“不知道”记录为“否”，也不能把假设记成事实。
- 用户只补充一个值：有唯一待澄清目标且上下文支持时更新；多个目标可对应时先确认。
- 插入闲聊或天气：允许作为独立任务响应，原待补充任务保留，不自动取消。
- 用户改条件：同一事项升版本，按依赖关系使旧候选和检查结果失效；不能继续确认旧草案。
- 多意图：明确依赖后执行；独立只读任务允许部分成功，单项失败不伪装成全部成功。
- 引用旧方案：使用稳定消息、事项或候选引用，不仅依赖截断上下文中的“第二个”。
- 未知请求：普通问答可以直接回答；无法核实的实时事实或系统外操作要说明边界。

首轮保留串行调度；待正确性和供应商限制验证后，再考虑独立只读查询的受控并发。

## 6. 上下文与记忆分层

### 6.1 保存全历史，不等于每次都发送全历史

| 层次 | 内容 | 使用方式 |
| --- | --- | --- |
| 用户可见对话 | 用户输入、最终回答、澄清和确认 | 界面展示；模型按任务选取相关轮次 |
| 业务状态 | 当前事项、来源、版本、未解决问题 | 核心事实依据，不被摘要替代 |
| 执行记录 | 工具请求、结构化响应、错误类别、耗时 | 排障与重放；模型通常只接收必要摘要 |
| 用户长期记忆 | 明确保存的偏好与历史行程 | 按身份查询、按相关性选取 |
| 企业政策 | 原文片段、文档版本及已审核规则 | 按公司与适用日期检索和核验 |

建议新增 `context.py` 负责输入组装，先做确定性的上下文选择和大小限制，再评估模型摘要。
预算通过 `Settings` 配置，包含模型输入上限、输出预留、工具结果上限和近期轮次上限。
支持 token 计量时按 token 管理；不支持时采用保守长度预算，并明确这只是估计。

必须保留当前输入、当前待澄清问题、相关事实来源和必要的工具调用配对。
不能截断成孤立的 ToolMessage；长工具结果保留结构化摘要与引用，不直接塞满上下文。
如果预算不足以安全解释用户引用，先定向读取历史；仍不明确时追问，不静默丢失关键内容。

### 6.2 长期记忆继续受控

- 不把所有聊天自动写成偏好，不自动把临时需求、假设或他人信息记到本人名下。
- 本轮明确需求优先于个人默认偏好；公司强制政策不能被偏好覆盖。
- 删除或修改后的偏好以存储中的有效版本为准，旧消息不能把它自动恢复。
- 摘要是派生数据，记录覆盖消息范围与版本，不能获得高于原始证据的权威。
- 首轮不增加跨会话向量记忆；只有真实需求证明精确读取不足时再单独设计。

## 7. 执行结果与输出

### 7.1 统一业务结果包络

建议专业模块返回统一外层协议，内部载荷保留原有领域契约：

```text
task_id / subject_id / revision
status: ok | needs_input | partial | empty | unavailable | error
data: 按领域验证的结果
sources: 供应商或政策来源、查询时间、版本
warnings: 未核验事项与限制
next_action: 当前允许的下一步
```

`empty` 只表示查询成功且无候选；`unavailable`、权限不足、超时不能被改写为“没有酒店”。
供应商标签、政策正文和记忆内容都按数据处理，不能成为覆盖系统指令的入口。
工具结果中的价格、时间、候选 ID、政策结论及未知状态由程序校验。

### 7.2 输出分工

政策结论、价格、日期和库存状态继续采用受约束的展示字段。
模型可以解释已验证结果，但解释失败时退回结构化展示，不让语言生成成为唯一可用路径。
“已保存”“已确认”“已预订”“已审批”分别对应真实动作，禁止相互替代。
保存成功必须在事务成功后展示；流式文字不是数据库提交证明。

## 8. 真正的流式交互与恢复

### 8.1 事件协议

建议使用现有认证方式下的 `fetch` 流读取，继续兼容 SSE 编码，不把访问令牌放进 URL。
沿用前端当前能力，分阶段增加事件，不一次性替换整个页面。

| 事件 | 产生时机 |
| --- | --- |
| `run_started` | 请求通过鉴权、归属和去重检查，运行已登记 |
| `task_update` | 任务或工具真实开始、完成、失败 |
| `answer_delta` | 已获准展示的回答增量；不转发槽位 JSON 或内部推理 |
| `confirmation_required` | 待确认信息已持久化，附事项及版本 |
| `run_completed` | 最终快照已提交，返回最终消息及检查点版本 |
| `run_failed` | 执行失败，提供脱敏错误代码与恢复提示 |

所有事件带 `run_id`、递增 `sequence` 和类型；必要时附 `task_id`。
前端用 `run_id` 更新对应的运行区域，避免切换会话后覆盖另一个会话的内容。
最终快照是展示完成结果的依据；连接断开或缺少完成事件不能显示“已完成”。

### 8.2 实现顺序

1. 先实现真实任务事件，解决整个执行期间页面无反馈的问题。
2. 再接入允许的最终回答增量，结构化抽取和语义复核输出不向前端直播。
3. 确定性生成的政策和候选结果在校验完成后立即展示，不假装它们是模型逐 token 生成。
4. 实现前核对本地固定版本的 LangGraph 流接口和嵌套工具事件传播行为，做小型探针验证。

不能只把 `invoke` 改名为 `stream`。当前同步工具、检查点连接、会话锁和响应生命周期需要一起设计。
首轮可在受管理工作线程执行同步图，通过有界队列发送事件；线程必须持有自己的连接和锁，
不得与响应生成器共享不安全的数据库连接，也不能以无边界后台任务替代恢复机制。

### 8.3 断线、幂等与重启

- 接收消息时先登记 `request_id` 与输入摘要；相同请求返回已有运行，不重复执行。
- 同一 ID 不同内容拒绝；确认操作额外校验待确认事项版本和授权。
- 同一会话同时只允许一个有效执行者，不同会话独立；复用现有数据库锁边界。
- 首轮允许短任务在网络断开后继续到有限超时，刷新通过运行状态和最终快照恢复。
- 不承诺断线后重放每个 token；增量可以丢失，最终结果不能靠重新提交用户消息恢复。
- 进程退出后的运行标为中断待核实，不自动重放有副作用操作。
- 业务写入保留原有版本检查和幂等机制；检查点与运行记录不同事务时，必须能对账，
  不能因缺少终态事件再次保存偏好或草案。

## 9. PostgreSQL 与兼容迁移

复用现有会话、偏好、行程及官方检查点表。新增任务状态优先放在图状态中，
避免同时维护独立任务表和检查点两套事实源。

为流式运行与幂等恢复，建议增加一张应用拥有的 `chat_runs` 表，表名为拟议名称：

- 记录身份范围、会话、请求 ID、运行 ID、输入摘要、状态、时间、最终检查点引用、脱敏错误。
- 唯一约束覆盖公司、用户、会话、请求 ID；状态查询也必须经过同样的归属校验。
- 不存模型原始内部推理，不重复保存密钥、完整供应商 URL 或大体积工具正文。
- 配置运行记录保留周期与清理策略；长期对话与运行日志不共用删除含义。

迁移使用版本化脚本和显式执行步骤，不修改 LangGraph 官方检查点表结构。
新增状态包含 `schema_version`；读取旧检查点时只做可验证转换，歧义状态要求重新确认。
含人工中断的旧线程必须单独验证节点恢复兼容性，不把旧确认直接映射到新动作。

上线前备份，在测试库验证迁移、旧会话恢复和幂等执行。
回退时先停止新写入并备份；确认旧版本能否读取新状态，不能直接切回后让旧代码误解检查点。
若不兼容，保留历史只读展示并要求创建新会话，明确告知用户，不能静默丢弃记录。

## 10. 可观测性与评测

### 10.1 先有基线，再改链路

第一阶段复用现有脚本记录：意图与任务完整性、字段和来源、追问、工具请求、返回状态、
最终回答、模型调用次数、修复次数、token 使用量（接口实际提供时）、阶段耗时。
区分理解错误、任务状态错误、供应商错误、政策检索错误、回答错误和前端错误。

日志默认只记脱敏标识、状态和耗时；原始对话仅在隔离测试环境及明确授权下保留。
首轮无需引入新观测服务；统一接口后再评估 Langfuse 等方案的部署与隐私成本。

### 10.2 测试分层

| 层次 | 核查内容 | 不能证明什么 |
| --- | --- | --- |
| 单元测试 | 契约、状态转换、字段撤回、版本失效、输出边界 | 不能证明真实模型理解正确 |
| 离线集成 | 脚本模型、供应商夹具、完整图路径及异常 | 不能证明外部服务可用 |
| 真实 PostgreSQL | 多用户隔离、重启、并发、幂等、确认和迁移 | 不能证明业务回答质量 |
| 真实模型与供应商 | 冻结场景、多轮补充、真实候选、错误说明 | 有限样本不能证明任意问题正确 |
| 浏览器验收 | 输入、流式状态、断线、新对话、切换、刷新和窄屏 | 不能以页面截图代替业务验收 |

冻结用例与验收标准应在实现前确定，并拆分开发集与保留集。
已经用于调试的保留题不再算未见题，需要新批次；不要只换城市和日期冒充泛化验证。
真实模型采用相同配置重复运行，报告样本数、运行次数、失败分布与不确定性。
模型评分仅作辅助；关键事实、权限、写入和工具行为优先由程序断言，争议结果人工复核。

### 10.3 首批验收矩阵

| 场景 | 必须观察的行为 |
| --- | --- |
| 酒店信息不全 | 只追问住宿所需字段；未调用供应商；不否认查询能力 |
| 酒店信息完整 | 只查酒店，不要求出发地，不额外查交通 |
| 单程交通 | 不追问酒店日期或强制返程 |
| 多轮修改日期 | 事项版本变化，相关旧结果失效，不确认旧草案 |
| 两个任务后补一个日期 | 依据待澄清目标归属；不明确时问清，不串事项 |
| 查询中插入其他话题 | 原任务保留，界面和任务状态不互相覆盖 |
| 否定、引用、假设、未知 | 不把非事实内容写为肯定事实，必要时澄清 |
| 没有候选与供应商超时 | 分别展示无结果和查询失败，不混为一谈 |
| 修改或删除偏好 | 使用有效记录版本；旧聊天不自动恢复已删偏好 |
| 两用户同名会话 | 消息、状态、偏好和运行信息不跨用户 |
| 刷新、断线、重复发送 | 恢复已有运行，不重复执行写入或覆盖其他会话 |
| 旧会话存在待确认动作 | 正确恢复或明确要求重新确认，不能误执行 |

### 10.4 发布门槛与报告

- 确定性关键断言必须全部通过：身份隔离、无伪造候选、无越权写入、旧版本确认拒绝、幂等。
- 真实质量指标分别报告，不能用总平均掩盖酒店单查或否定理解等单类失败。
- 首轮建议业务任务通过率目标不低于 90%，这是待基线后确认的项目目标，不是已达成结果；
  同时必须对关键类别逐项判定，原先失败的目标行为应有明确改善。
- 真实模型出现的严重虚构、错误持久化或越权属于阻断问题，即便总分达标也不发布。
- 响应速度记录首个真实进度事件、首个回答增量和总耗时的 P50/P95；先测基线再设阈值。
- 外部服务不可用的用例列为受阻，不计为业务通过；验证错误呈现可以另计为异常处理通过。

每份验收报告包含版本与配置摘要、问题及多轮输入、实际回答、关键调用、预期行为、
通过/失败/受阻、证据路径、失败原因及未解决项。正文脱敏，不泄露密钥与个人信息。

## 11. 分阶段实施

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 基线与最小追踪 | 复用评测脚本，冻结用例，记录阶段错误与耗时 | 失败可定位，开发集与保留集边界明确 |
| P1 查询契约 | 酒店、交通、组合请求；按组件执行及校验 | 单查不被无关字段阻断，旧完整行程回归通过 |
| P2 任务生命周期 | 澄清目标、版本失效、依赖、部分成功与中断兼容 | 多轮更正、不串事项、旧确认拒绝通过 |
| P3 上下文分层 | 任务上下文构建、预算、证据与偏好版本约束 | 保留集不退化；长对话与指代场景通过 |
| P4 运行与流式 | 运行表、幂等、真实事件、回答增量、刷新恢复 | 并发、断线、重启、移动端与确认流程通过 |
| P5 整体验收 | 真实对话、供应商、数据库与浏览器联合报告 | 关键门槛满足；未通过项显式列出 |

每阶段独立提交、验证和交付，不一次性重写整个系统。
上下文新策略先在评测环境对照，再逐步启用；生产影子执行不能重复副作用工具。
快速通道优化在 P2 后按耗时证据加入：仅用于经过鉴权和版本校验的明确界面动作，
不能让前端声明的意图绕过必填、授权或结果校验。

## 12. 验证方式与实施前确认

现有工具链为项目 `.venv` 与 pip，依赖固定在 `requirements.txt`。
以下是后续实施的验证入口，本次编写方案未运行这些业务测试：

```powershell
# 在项目根目录执行
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -q
.\.venv\Scripts\python.exe -m pip check

# 仅在已确认隔离测试库和访问权限后启用真实数据库测试
$env:TRAVEL_TEST_POSTGRES='1'
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -q
```

真实模型评测复用 `scripts/acceptance_chat.py` 等入口，实施阶段先核对参数、用例格式与费用预算。
供应商验收仅查询，不下单、不支付。端口、凭据或数据库不可用时报告阻碍，不擅自改配置绕过。

需要确认的不是重新选择框架，而是实施授权、测试费用上限、发布门槛，以及 P4 数据库迁移窗口。
P0 先给出基线，再据证据调整后续工作量；不以换模型或扩大架构掩盖基础契约问题。
