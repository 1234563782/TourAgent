# 意图识别彻底重构方案

> 状态：设计文档（待实施）　日期：2026-08-24
> 说明：本文档只描述改造方案，实施时另行执行，不随本文档改动任何代码。

## 1. 背景与问题

当前 `agents/intention_agent.py` 的意图识别是「一次 LLM 自由文本调用 → 手写 JSON 解析兜底」，存在 6 个问题：

1. **置信度白算**：模型产出 `confidence`，但编排器从不读取，无阈值、无澄清。
2. **理解与调度耦合**：一次调用同时输出「用户想干什么」和「调谁、什么优先级」，Prompt 过长、格式脆弱。
3. **priority 由 LLM 决定**：优先级规则其实是写死的业务规则，却交给模型输出，引入不确定性。
4. **event_collection 混在意图里**：它是内部流程步骤，不是用户意图。
5. **兜底粗暴**：任何失败统一降级成 `information_query`，答非所问。
6. **无结构化输出约束**：靠事后 `json.loads` + 多层清洗补锅，未复用已有的 `utils/json_parser.py`。

**目标**：把意图识别改造成**分层 + 结构化输出 + 确定性路由 + 置信度澄清闭环**，接近主流生产做法，同时保持 6 个 skill 插件的懒加载机制不变。

**已确认方向**：改造深度 = 彻底重构；低置信度行为 = 反问澄清。

---

## 2. 目标架构

```
用户输入
  │
  ▼ 第0层：命令拦截（help/exit/status/clear/history/preferences/health）—— 已在 cli.py，保持不变
  ▼ 第1层：规则快路由（utils/rule_router.py）—— 高频明确意图直接命中，省一次 LLM 调用
  ▼ 第2层：结构化意图识别（StructuredIntentRecognizer）
  │     输入：query + 上下文 + 时间 + skill 描述
  │     输出：{ intents:[{type, confidence, reason}], key_entities, rewritten_query,
  │             needs_clarification, clarification_question }
  │     方式：requests 直连 OpenAI 兼容端点 + response_format={"type":"json_object"} 强制 JSON
  ▼ 第3层：确定性路由（agents/intent_router.py）—— intent → [(agent_name, priority)] 查表
  ▼ 第4层：置信度决策 —— max_confidence < 阈值 或 needs_clarification → 反问用户
  ▼ 编排器 OrchestrationAgent —— 消费确定性 schedule（改动最小）
```

## 3. 改动清单

### 3.1 `config.py` —— 新增配置（禁止硬编码）

```python
INTENT_CONFIG = {
    "clarify_confidence_threshold": 0.6,   # 低于此值 → 反问澄清
    "low_confidence_threshold": 0.4,       # 低于此值 → 只澄清，绝不执行
    "response_format": "json_object",      # 结构化输出模式
    "max_intents": 3,
}

ROUTING_CONFIG = {                          # 确定性路由映射表
    "itinerary_planning": [("event_collection", 1), ("itinerary_planning", 2)],
    "preference":         [("preference", 1)],
    "information_query":  [("information_query", 1)],
    "rag_knowledge":      [("rag_knowledge", 1)],
    "memory_query":       [("memory_query", 1)],
}
```

### 3.2 新增 `utils/structured_llm.py`

- 封装 `async def structured_call(messages, schema)`：用 `requests`（项目已有依赖）直连 `LLM_CONFIG["base_url"]/chat/completions`，带 `response_format={"type": "json_object"}`，通过 `asyncio.to_thread` 包装同步请求。
- 复用 `utils/json_parser.py` 的 `robust_json_parse` 做解析。
- 新增 `validate_schema(data, schema)`：手写轻量校验（intents 非空、confidence ∈ [0,1]、字段齐全），不引入 `jsonschema` 重依赖。
- 失败时返回 `None` + 错误信息，由调用方决定澄清，而非伪装成某意图。

**理由**：绕开 agentscope 1.0.16 是否支持 `response_format` 透传的不确定性；意图识别层独立、可控；其余 6 个 skill agent 仍用 agentscope model，不受影响。

### 3.3 新增 `utils/rule_router.py`（第1层规则打底）

- 少量高频、零歧义规则，命中即返回确定性路由，跳过 LLM：
  - 含「天气/气温/下雨/预报」→ `information_query`
  - 含「标准是多少/如何报销/报销」→ `rag_knowledge`（与 RAG 触发词对齐）
- 未命中返回 `None`，继续走 LLM。保持克制，规则只做「明确命中」，不做「排除」。

### 3.4 重构 `agents/intention_agent.py`

- 输出契约从 `{reasoning, intents, key_entities, rewritten_query, agent_schedule}` 改为：
  ```
  { intents, key_entities, rewritten_query,
    needs_clarification, clarification_question }
  ```
  —— 移除 `agent_schedule` 与 `priority`（交给 router）；`reasoning` 保留为可选调试字段，不进调度。
- Prompt 里去掉「第4步结构化决策」和「优先级分组」两段，只保留理解三步：推理、多意图识别、Query 改写。
- 意图枚举收窄为 5 个用户可感知意图：`itinerary_planning / preference / information_query / rag_knowledge / memory_query`（`event_collection` 移除）。
- 改调 `utils/structured_llm.structured_call`，删除手写 JSON 解析兜底；解析/校验失败时返回 `needs_clarification=True` + 通用追问，不再伪装成 `information_query`。
- 置信度由模型输出，作为软信号（仍非严格校准概率，但配合澄清闭环可用）。

### 3.5 新增 `agents/intent_router.py`

- `def route(intents) -> agent_schedule`：查 `ROUTING_CONFIG`，多意图按出现顺序合并去重；未知/表外意图告警并忽略。
- `def decide_clarification(intents) -> bool | question`：结合 `INTENT_CONFIG` 阈值 + `needs_clarification` 判断是否反问。
- 纯函数、无 IO，可离线单元测试。

### 3.6 重构 `cli.py` 的 `process_query`

- 调用链改为：`rule_router → structured 意图识别 → intent_router.route → 澄清决策 → orchestrator`。
- 新增澄清循环：命中澄清时用 `Prompt.ask` 反问用户，把用户回答并入上下文后重新走一遍意图识别（单次追问即可，避免死循环，设最大追问 1~2 次）。
- 保持 `retry_with_backoff`、熔断器逻辑不变。

### 3.7 微调 `agents/orchestration_agent.py`

- 仍从输入 JSON 读 `agent_schedule`，但该字段现在由 `intent_router` 确定性生成；确认对 `preference` 记忆写回等逻辑无破坏即可，接口对齐则无需改动。

### 3.8 修复/新增测试

- `tests/test_intent_router.py`（新增）：纯单元测试路由映射 + 澄清决策，**离线可跑、不依赖 LLM/网络**。
- `tests/test_intention_agent.py`（更新）：适配新输出契约（去掉 `agent_schedule`，展示 `needs_clarification`）。
- `tests/test_orchestration.py`（修复）：把失效的 `from agents.event_collection_agent import ...` 改为经 `LazyAgentRegistry` 或 `.claude/skills/*/script/agent.py` 加载。

## 5. 关键设计决策

- **结构化输出用 `response_format=json_object`，而非 function calling**：意图分类是「返回结构化结果」，json_object 更贴切、豆包/火山方舟兼容性更好；function calling 更适合「返回工具调用」。若目标 API 支持 `json_schema`，可进一步用 JSON Schema 强校验（后续增强，非本次必做）。
- **event_collection 从「意图」降级为「路由内部步骤」**：`itinerary_planning` 意图自动带上 `event_collection`(P1) + `itinerary_planning`(P2)，skill 本身保留不动。
- **置信度闭环**：LLM 自报置信度 + 阈值 + 反问，作为软信号使用；硬保证靠结构化输出与确定性路由。

## 6. 验证方式

1. **离线单测（不依赖 LLM/网络）**：`python tests/test_intent_router.py` —— 验证路由映射与澄清决策正确。
2. **结构化调用连通性**：`python cli.py health` 验证 LLM 端点可达（需先在 `config.py` 填入真实 api_key/model_name）。
3. **意图识别端到端**：`python tests/test_intention_agent.py`（需真实 key）—— 覆盖行程规划 / 偏好 / 天气 / 知识库四类，观察 `intents`、`needs_clarification`、`clarification_question`。
4. **澄清闭环**：`python cli.py` 输入模糊句（如「北京怎么样」），确认系统反问而非硬调度。
5. **回归**：`python cli.py` 跑一遍「从上海到北京出差，喜欢住汉庭」，确认最终行程正常生成。

## 7. 风险与 fallback

- **风险 1：目标 LLM 端点不支持 `response_format`** → `structured_llm` 捕获 400/不支持错误，自动降级为「普通调用 + robust_json_parse + schema 校验」，仍能跑通（等价于加固版现状）。
- **风险 2：agentscope 未安装（当前环境 `ModuleNotFoundError`）** → 意图识别层用 requests 直连、不依赖 agentscope；实施时先 `pip install -r requirements.txt` 装齐依赖再验证。
- **风险 3：澄清追问导致死循环** → 设最大追问次数（默认 1 次），超限则按最高分意图执行并提示。
