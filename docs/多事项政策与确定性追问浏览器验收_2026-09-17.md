# 多事项政策与确定性追问浏览器验收

日期：2026-09-17，Asia/Shanghai。

## 结论

最终连续两批真实浏览器验收均为14轮、17项检查全部通过；776项Python测试含PostgreSQL零跳过，Node流式协议5项与依赖检查通过。

这证明本报告列出的流程在两批运行中通过，不代表任意自然语言都能正确回答，也不代表所有答案质量已经合格。仍有条款范围转述、冗长及酒店参考报价预算提示问题，详见末节。

## 范围与方法

- 使用现有本地虚拟环境、FastAPI、LangGraph、PostgreSQL政策库、配置的真实模型与酒店服务，不新增依赖。
- 通过Playwright实际操作Edge：登录、建立会话、在输入框提交问题、等待流式请求完成、读取回答和事项状态、刷新页面。
- 每批创建随机账号、随机端口及独立`travel_auth_browser_*`数据库schema；结束后清理，不改正式账号、政策或密钥。
- 读取当前学校政策`hfut_travel / 2026-project-v1`。按项目采用口径使用现有资料，不要求用户确认政策生效日期。
- 不只看回答关键词，还核对事项ID、版本、执行次数、事实、更正与撤回、附表查询和引用。多事项更正时比较未涉及事项的完整快照。
- 每轮保存全部政策调用，而非只保存最后一个事项；完整实录在各批`summary.json`、`extraction.json`、`policy-explanations.json`和`policy-stages.json`。
- `policy-stages.json`的`turn`是政策调用计数，不应直接当成浏览器用户消息轮次；用户14轮以`summary.json.turns`为准。
- 人工查看1440和390宽度截图：输入框和发送按钮存在，无明显横向溢出。手机布局较长，聊天区域仍需内部滚动，本轮未改造布局。

## 发现与改动

扩展测试首次出现同轮两事项失败：成都和厦门均独立建账，精确附表查询及回答草稿金额正确，但复核对两个事项各拒绝两次，给出`incomplete_answer`、`intent_changed`。工作流最终返回依据不足，而不是返回正确答案。

优先假设是复核将整轮原话的全部要求当成单个事项的职责。此次改动：

1. 图向政策工作流传递当前事项的`scoped_request`，同时保留完整本轮原话、原始请求、事实来源、事项ID、版本及本轮更正。
2. 明确回答与复核仅覆盖当前事项；没有回答另一事项不应被认定为本事项遗漏。
3. 明确范围文本不是独立证据，不能靠它与改写问题相等证明改写正确；本事项相关的用户否定、更正、撤回仍必须核对，冲突以原话为准。
4. 保留引用连续摘录检查、政策版本门禁和独立复核，没有直接放行草稿，也没有按城市、金额或测试问句写生产分支。
5. 新增真实图的双事项契约测试，验证writer/reviewer均收到独立事项与完整用户证据；既有多轮回归补充范围断言。

这是上下文契约和模型指令边界修正，不是把语义复核变成确定性算法。两批复验支持该方向有效，但没有通过大样本对照证明唯一根因或长期误拒率。

## 未解决与下一步

1. **条款范围转述仍有偏差。** 第一批第8轮把“差旅费实行凭据报销与定额包干相结合”转述成“住宿费实行……”，引用存在不等于适用范围准确。第二批没有重复这句，但不能因此宣称已经修复。优先补条款主体、对象、例外的独立验收。
2. **酒店预算推荐提示不充分。** 第二批用户预算每晚400元，展示搜索参考价429元、房型418/424元，却仅提示口径未知和不能确认合规，缺少醒目的“参考报价数值已高于预算”提示。计价口径未知时不能直接认定实际超预算，也不应让不确定性掩盖价格差异。下一步应单独设计可比口径下的代码比较、不可比时的风险提示及候选排序。
3. **回答偏长。** 只问计价单位仍举无关地区金额；酒店事实来源逐字段重复，移动端阅读负担较大。本轮未调整渲染或强行截断答案。
4. **自然语言泛化未保证。** 本轮只有一个新增双事项表达及其更正/撤回，重复两批不是大规模独立测试集；不能宣称消除了所有改写、归属与复核错误。
5. **外部报价完整性与观测边界。** 含税、每晚/全程口径、响应日期和最终库存仍需核实；本轮未验收Langfuse云端回读，也未做并发压力或完整安全审计。

建议下一轮优先处理条款主体/适用范围和酒店预算提示，继续用代码校验可确定的字段、数值和状态，保留模型对模糊自然语言的解释职责。
