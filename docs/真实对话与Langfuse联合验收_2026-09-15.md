# 真实对话与 Langfuse 联合验收

日期：2026-09-15，Asia/Shanghai。

## 结论

两批真实浏览器分别完成11轮对话，14项业务检查全部通过。历史酒店合规追问失败在本次两批中未再出现。
第二批真实 Web/SSE 请求对应的11条云端追踪、134个观测通过结构、结束状态及隐私检查。
这是本轮指定范围通过，不是“所有场景永远正确”，也不是对任意新问法的统计可靠性证明。

首批云端结构检查报错保留：原因是新增验收脚本对SDK根节点的判断不正确，不是酒店业务失败。
本轮未改生产业务代码、模型、密钥、规则、提示词或真实用户数据；不需要为验收脚本重启正式服务。

## 验收方法

1. 使用项目已有 Python 虚拟环境、系统 Edge 与已有 Playwright，不安装新依赖。
2. 创建随机隔离 PostgreSQL schema 和临时测试用户；保持真实政策公司的只读访问。
3. 浏览器实际填写账号、登录、输入消息、点击发送，经过真实 FastAPI、SSE、LangGraph、模型及酒店供应商。
4. 每轮读取服务端任务账本和工具证据，不只看页面文字。验证任务ID、事项ID、版本递增、查询次数、参数、候选来源和落盘结果。
5. 对合规追问严格验证：不修改旧任务、不新增实际费用、不重放酒店查询，必须调用只读结果工具。
6. 刷新后核对最后回答；检查浏览器脚本错误，保存1440、390和320宽度截图。另用内置浏览器打开正式8000，确认登录页可读。
7. 在测试包装器中捕获真实请求的trace ID及应用根观测ID，用已配置SDK回读云端。完整问题和回答仅保留本地。
8. 临时服务退出后删除本批临时schema；正式服务和历史对话不动。

两批每轮耗时包含从发送到页面完成及读取状态，不是首token延迟。第二批约3.96至10.29秒。

## 失败与修正

首批业务14项通过，云端11条均被新增脚本判为 `connected=false`，其他云端检查均通过。

依次排查：真实子节点断链、SDK虚拟根父节点、测试判断错误。
只读回查首条追踪的ID和父ID发现，所有业务子节点都正确连到chat，只有chat指向一个未导出的父节点。
本地固定SDK4.15.2源码 `_create_remote_parent_span` 证实：仅传trace ID时，它会生成随机 `NonRecordingSpan` 父节点。

修正的是验收边界，不是业务：

- 在Web测试包装器中捕获应用真实创建的根观测ID。
- 云端严格查找这个根，再检查每个子节点能否连接到它。
- 错误根、子节点断链、循环、重复ID、未结束、跨trace和正文泄漏仍会失败。
- 新增测试先因缺少root_id接口失败，实现后29项观测/证据定向回归通过。
- 真实SDK离线导出也覆盖此检查；第二批真实浏览器和云端全部通过。

首批原始失败文件没有修改或删除。

## 未解决与未覆盖

- 回答冗长：只读追问会重复完整事实和结果，答案重点被埋在长文本中。不是本轮正确性失败，但需要展示层改进。
- 移动布局：390宽截图中，账户信息、会话标题占据较多顶部空间，输入框位于页面较下方；本轮没有声明手机首屏体验通过。
- 模型异常后未提交的更正信息如何在下一轮承接，是历史待修事项；本轮没有触发该故障，不能宣称已解决。
- 没有在真实供应商上故意制造超时/空结果，未真实重测天气、交通、地图、跨账号并发或所有RAG问答。相关本地测试通过不等于真实全场景验收。
- 供应商报价口径仍不完整；系统正确保留“不能确认合规”，不能为了给确定答案而把参考起价当实际含税房价。
- 两批同一主流程包含城市、日期和措辞变体，但样本量有限，不能据此承诺任意问法可靠率。

下一步建议优先处理失败请求后的更正承接，再优化短结论/可展开依据和移动端布局；不需要为本次通过继续添加Agent或更换模型。
