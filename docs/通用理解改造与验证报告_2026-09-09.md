# 通用理解改造与验证报告

日期：2026-09-09。结论：核心协议和编排已改造，尚未全部验收通过。

## 目标与实施

目标是减少依赖固定问法的语义特判，而不是承诺任意问题都能正确回答。
本轮未修改真实 `.env`、政策金额或正式用户记忆，没有下单或支付。

| 模块 | 已实施的修改 |
| --- | --- |
| `business_travel/slots.py` | 统一为任务数组；携带近期对话；机械暂存后经语义复核原子提交；保存事项ID和版本，支持跨轮定位 |
| `business_travel/semantic_review.py` | 无副作用的结构化复核；提供原话、上下文、状态和业务schema；异常或拒绝时不提交 |
| `business_travel/graph.py` | 多任务逐项执行、逐项保留结果；确认恢复不重复执行已完成的前序任务 |
| `business_travel/policy_guard.py` | 移除短语支持判定和遗漏字段启发式；不将原文子串存在当作语义证明 |
| `business_travel/contracts.py`、`tuniu.py`、`policy_pg.py` | 从供应商结构化字段规范化交通方式和席别，再接入已有政策规则；未知字段不猜测 |
| 配置 | 上下文窗口和任务上限可配置；只更新配置示例，没有改真实凭证 |

保留确定性的业务规则与事实呈现。结构化工具调用只约束协议；
复核模型的accept不是语义正确、审批成立或费用可报销的证明。

## 怎么验证

离线命令：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -q
```

本轮收尾重跑：245项，224通过，21项真实数据库测试跳过，耗时8.722秒。
覆盖协议拒绝、整批原子提交、多事项、归档事项更新、同日两笔费用、
确认恢复、交通席别规则桥接等。脚本模型只验证控制流，不证明真实语义能力。

真实模型探测入口为 `scripts/verify_semantic_slots.py`，不连接业务数据库或供应商。
普通模式调用真实提取和复核；`proposal`模式注入错误提案，仅调用真实复核。
两类结果分开解释，不把注入提案称为模型实际提取错误。
原话、预期、模型工具调用、结构化结果及失败判定保存在各目录的 `results.json`。

历史失败未删除，第三轮成功不能覆盖前两轮失败，也不能证明模型总是正确。

## 未通过的问题

用户原话：

> 核对餐补，单位只承担午饭费用，早晚饭我自己掏钱。

测试故意注入 `covered_meals=["breakfast","dinner"]`，并附完整原文引用。
预期：复核拒绝，因为单位承担的是午餐，早晚餐是自付。

实际：真实复核输出 `verdict="accept"`、`issues=[]`，
错误值进入 `context_reviewed` 状态。此项失败仍未修复。
这不是“某句需要再加一个特判”的证据，而是模型复核仍会误判的直接证据。

## 剩余工作与验收边界

1. 关键事实需要进一步设计可信来源或显式确认边界，尤其审批状态、费用归属等
   会改变核验结果的字段。用户自述、模型复核、用户确认和企业系统凭据不能混为一谈。
2. 如引入独立抽取比对或不同模型复核，必须保留不一致时的澄清路径，
   并用新样本验证；增加调用次数本身不是正确性保证。
3. 尚未实现受依据约束的自由语言回答组织，目前继续保留确定性结果呈现。
4. 本轮没有完成真实PostgreSQL、供应商和前端端到端回归；
   旧版全通过报告不能作为本轮改造后的端到端证据。
5. 后续评测应覆盖新问法、多轮纠正、多事项交叉、拒绝与工具失败，
   同时检查最终回答，而不只检查工具是否执行成功或JSON是否合法。

当前可以确认的是协议和流程覆盖有所扩展，不能宣称泛化问题已经彻底解决，
也不能以本报告作为企业报销审批或生产上线的可靠性保证。
